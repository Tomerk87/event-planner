# Architecture decisions

Records the technical decisions approved in `AGENTS.md` and `PLAN.md`, plus the choices that are still open. Product behavior lives in `docs/PRD.md`; this file does not restate it.

Update this file when a decision is made or changed. Do not record a choice here as decided until it has actually been adopted in the repository.

| Demo data | Generated by a seeded generator (`services/mock/generator.ts`) with a fixed seed and dataset version; dates are placed relative to the first launch. About 374 KB as stored | Adopted in Phase 3 |

| Stored-data versions | The demo dataset has `DATASET_VERSION` (`services/mock/state.ts`); a browser holding another version regenerates the demo once and says so. Real accounts' data is in PostgreSQL and is changed only by migrations | Adopted in Phase 5 |
| Charts | Drawn with SVG and CSS inside the feature that needs them; no charting library. Every chart also states its figures as text or a table | Adopted in Phase 5 |

CSV is read and written by `frontend/src/domain/csv.ts`, with a UTF-8 byte-order mark so Excel opens Hebrew. Files are read in the browser and sent nowhere. The npm `xlsx` package was rejected as outdated with known vulnerabilities, `exceljs` as about ten times larger | Adopted in Phase 6 |
| Formula safety in exports | `neutralizeFormula` in `domain/csv.ts` writes a cell that would run as a formula as plain text; Excel cells are typed as text. Guest-typed values reach these files | Adopted in Phase 6 |
| Display preferences (guest columns, collapsed side menu) | `PreferencesService` in the service contracts, implemented once (`services/preferences.ts`) and used by both sources: kept per browser under `event-planner.preferences`, never on the server (D86) | Adopted in Phase 6, shared in Phase 16 |
| Tables | Data tables are built with `shared/ui/DataTable.tsx`, which centres every heading. A column sets `align: 'center'` for numbers, `wrap` for long text that may break when room is short, and `pinned` with `hideHeader` for the actions column at the end, and `onRowClick` to make each row (each card on a phone) choosable by a click or by Enter or Space, ignoring clicks on the row's own controls. English headings are Title Case. A table that cannot use `DataTable` (the import preview) follows the same rules in its own styles | Owner decision 2026-10-13 |
| Dropdowns | `shared/ui/Select.tsx` is the one dropdown: a button with the `combobox` role and a `listbox`, with arrow keys, Home/End, typing to jump and Escape. `SelectField` wraps it and still takes `<option>` children. With `searchable` the field becomes a text box whose typing narrows the list (used for "Preview for"). The list is positioned against the screen, so a scrolling table or dialog cannot cut it off, opens upwards near the bottom, and follows its button on scroll. `shared/ui/Combobox.tsx` (text entry with suggestions) shares its list styles (`Listbox.module.css`). Tests use `chooseOption` (`src/test/controls.ts`, `e2e/helpers.ts`) | Owner decision 2026-10-13 |
| Nested dialogs | A dialog may open another (the new-group confirmation inside the guest form). `useModalDialog` ignores close events that come from a dialog inside it, because React passes them on to the dialogs around | Found after Phase 8 |
| WhatsApp sending | `buildWhatsAppUrl` in `domain/messages.ts` builds the `wa.me` link; the provider returns it (`MessagePreview.launchUrl`) and never opens anything. The page opens it with `shared/openExternal.ts` directly from the user's click, before recording the send, so browsers do not block it as a pop-up. Tests replace `window.open` | Adopted in Phase 8 |
| Address state helper | `frontend/src/shared/useQueryParams.ts` applies each change on top of the last change requested, so quick successive changes are not lost | Adopted in Phase 6 |
| Session | `SessionProvider` (`frontend/src/app/session/`) asks the backend who is using the application and gives the pages the data operations of that session; route guards send a signed-out visitor to the landing page. An open demo is remembered in `event-planner.session` (persistence adapter); otherwise `GET /api/auth/me` is asked, and the account session itself is the httpOnly cookie. When an account request is answered 401 (session expired or revoked), `Backend.onSessionEnded` returns the application to signed out; the start-up check for a session never counts as one ending. The browser-local preview accounts of the prototype (`event-planner.accounts`) were removed in Phase 16 and their key is cleared on load (D85) | Adopted in Phase 4, changed in Phase 16 |
| List state in the address | A list page keeps its filter, search and layout in the page address (query string), so a reload keeps them without using browser storage | Adopted in Phase 4 |
| Loading and error state | TanStack Query. Demo data changes only through mutations, which invalidate what they affect | Adopted in Phase 3 |
| Phone numbers | `frontend/src/domain/phone.ts`. `normalizePhone` turns any accepted form into one canonical form used for matching and uniqueness; a number without `+` is read as Israeli, and one local to another country is refused. `formatPhone` gives the form shown: local for Israeli numbers, with the country code for others. Guests and unknown responses store the shown form, so screens and exports agree | Adopted in Phase 3, extended after Phase 6 |
| Localization | `i18next` + `react-i18next`; locales `en` and `he`; root `lang`/`dir` follow the active locale; CSS logical properties | `AGENTS.md` Internationalization |
| Backend | Node.js + NestJS 12 in `backend/` (TypeScript strict, ESM, npm). Thin controllers; rules in services that call `backend/src/domain`. Same tooling as the frontend: oxlint, Prettier, Vitest | `AGENTS.md`; adopted in Phase 13 |
| Database | PostgreSQL 17, Prisma 7 with the `pg` driver adapter. Schema in `backend/prisma/schema.prisma`, migrations in `backend/prisma/migrations/` (reviewed SQL, including CHECK constraints for attendee bounds, RSVP/count consistency, table and event limits). Development uses a database-only container (`backend/docker-compose.dev.yml`) with a separate `event_planner_test` database | Adopted in Phase 13 |
| Shared business rules | `backend/src/domain/` is a copy of `frontend/src/domain/` (plus the new-event defaults), so both apply identical rules; the backend copy is authoritative. `sameAsFrontend.test.ts` fails when the copies differ, so a rule is always changed in both, in the same change | Adopted in Phase 13 |
| API contract | REST under `/api`, described by OpenAPI generated from the NestJS request/response classes (Swagger plugin). Served at `/api/docs`; `backend/openapi.json` is written by `npm run openapi`. The frontend's API provider (`services/api/`) uses the shared domain types, which the responses are; `apiServices.test.ts` checks that every route it calls is in `openapi.json`. Generating types (`openapi-typescript`) was not adopted: it requires TypeScript 5 and the frontend uses 6. Errors are `{ code, details }` with the `DomainError` codes and a matching HTTP status | Owner decision 2026-10-14; adopted in Phase 13 |
| Authentication | Email + password. Passwords hashed with argon2id. A random session token in an httpOnly, SameSite=Lax cookie (`ep_session`, Secure in production); only its SHA-256 hash is stored, in the `Session` table, so sessions can be revoked. 30-day sessions. Every route requires a session unless marked `@Public()` (global `SessionGuard`). Sign-in and sign-up are limited to 10 attempts a minute per address. A failed sign-in does not reveal whether the account exists | Owner decision 2026-10-14; adopted in Phase 14 |
| Email verification | None for the POC: invitations to an email are accepted when that email signs up. Must be added before real users (`PLAN.md` Phase 17) | Owner decision 2026-10-14 |
| Event access on the server | `EventAccessService` resolves the user's role in the event (a Super User counts as Owner) and checks every event-scoped action with `assertCan` from the shared rules. An event the user cannot reach answers 404, never 403. Super User is set only with `npm run super-user` | Adopted in Phase 14 |
| Concurrency | Changes to an event's guests and memberships run in a transaction that first locks the event's (or its memberships') rows, so uniqueness, capacity and last-Owner checks see what is really stored | Adopted in Phase 14 |
| Guest files on the server | `POST …/guests/import/read` parses an uploaded CSV/XLSX (5 MB, 5,000 rows) into rows for the import dialog; `POST …/guests/import` adds the chosen rows with the same rules, all or none; `POST …/guests/export` writes CSV/XLSX with headings supplied by the client in the person's language | Owner decision 2026-10-14; adopted in Phase 14 |
| Event operations on the server | Messages (template, variable values, preview, send, sent list), RSVP Settings, the public RSVP page, tables with the seating export, and the Dashboard, each a NestJS module (`backend/src/messages`, `rsvp`, `tables`, `dashboard`) calling the shared rules. A send adds one to the guest's counter and records the send in one transaction; it is an initiation, not a confirmed delivery. The Dashboard is computed on each request from the stored records with `domain/metrics.ts`, so it always matches the demo's figures. The RSVP link in messages uses `PUBLIC_APP_URL` (the frontend origin by default) | Adopted in Phase 15 |
| Public RSVP limits | Decision D2. Per IP address: a named `@nestjs/throttler` limit on the submit route only (`RSVP_LIMIT_PER_IP`, default 10). Per phone: `AttemptLimiter` in `RsvpService`, counting accepted answers per event and normalized phone (`RSVP_LIMIT_PER_PHONE`, default 3). Both over `RSVP_LIMIT_WINDOW_MINUTES` (default 10). Counts are kept in the server's memory: one process on one VM, and a restart only clears them. Behind Nginx, `TRUST_PROXY_HOPS=1` must be set, or every guest appears to come from the proxy's address and shares one limit | Owner decision 2026-10-14; adopted in Phase 15 |
| API provider | `frontend/src/services/api/`: `http.ts` (fetch with the session cookie; an error body `{ code, details }` becomes the same `DomainError` the demo throws; a server that cannot be reached is `UNAVAILABLE`), `apiServices.ts` (each contract method to its route, sending only the fields the API accepts) and `apiBackend.ts` (sign-up, sign-in, the session, sign-out). In development Vite forwards `/api` to `http://localhost:3000` (`API_URL` to change it), so the cookie stays on one origin, as Nginx does in production. Queries retry once only when the service could not be reached, and reload on returning to the window (D67) | Adopted in Phase 16 |
| Guest and seating files | `FilesService` in the contracts (`readGuestFile`, `exportGuests`, `exportSeating`). The demo reads and writes files in the browser (`services/spreadsheets.ts`); a real account uploads the file to the server and downloads what it writes (D83). The size limit is checked before uploading | Owner decision 2026-10-14; adopted in Phase 16 |
| Request size | The API accepts JSON bodies up to 5 MB (pictures as data addresses, imports of 5,000 guests); a larger request is refused with `VALIDATION` (413) | Found in Phase 16 |
| Email | Decision D88. `backend/src/email/`: a `Mailer` (`NullMailer` logs only the kind of email; `SmtpMailer` sends with nodemailer) chosen by `EMAIL_MODE` (`off` by default, or `smtp` with `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM`), and `EmailService`, which limits each kind of email to `EMAIL_LIMIT_PER_HOUR` (default 3) per address and logs a failed send without failing the request. Texts in English and Hebrew are in `email/templates.ts`, laid out as in `mockups/event_collaboration_email.png` (D93) with table-based HTML and inline styles, plus a plain-text version; the pictures are PNG files sent inside the email as inline attachments (`cid:`), drawn by `frontend/scripts/email-images.ts` into `email/images.ts`. Links are random tokens stored only as hashes in `EmailToken`, used once inside one statement, expiring after `EMAIL_VERIFY_HOURS` (24) or `PASSWORD_RESET_MINUTES` (60). Forgot password answers before preparing the email, so neither the answer nor its timing reveals an account. Amazon SES is used through its SMTP endpoint in production (Phase 18); Mailpit, in `docker-compose.dev.yml`, catches every email locally (http://localhost:8025) | Owner decision 2026-10-15; adopted in Phase 17 |
| System settings | `GET /api/system/features` (public) tells the frontend whether email is on; `GET /api/system/email` and `POST /api/system/email/test` are for Super Users only and never return the SMTP user or password (D91) | Owner decision 2026-10-15; adopted in Phase 17 |
| Notifications | Decision D95. `backend/src/notifications/`: the `Notification` table (kind, event id and name, who did it, role, read time); `notify()` and `notifyUnknownRsvp()` write notices inside the transaction of the change (permissions, sign-up and verification, public RSVP). `GET /api/notifications` lists the newest 30 and the unread count, dropping notices older than 90 days; `POST /api/notifications/read` marks one (`id`) or all read. The frontend's bell polls every minute and on window focus | Owner decision 2026-10-15 |
| Floor plan | Decision D100. Geometry and validation in `domain/layout.ts` (both copies): sizes in centimetres, table sizes and chairs from shape and seats, overlap checks by separating axes. Server: `backend/src/layout/` with `GET`/`PUT /api/events/:id/layout`; the room, floor-picture settings and `layoutVersion` on `Event`, a table's `x`/`y`/`rotation` on `EventTable`, objects in `VenueObject`; the picture is stored like the RSVP picture. The plan is saved whole and a stale version is refused (409 `LAYOUT_CHANGED`). Frontend: `features/event-layout/FloorPlan.tsx` draws it as SVG with pointer events (drag, pinch, Ctrl/⌘-wheel zoom, keyboard), no drawing library; `ArrangementTab.tsx` holds View and Edit modes | Owner request 2026-10-16 |
| API response headers | Every answer carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`, without `X-Powered-By`. In production the server refuses to start unless `CORS_ORIGIN` and `PUBLIC_APP_URL` are HTTPS (the session cookie is `Secure` there), and `/api/docs` is not served (D92) | Adopted in Phase 17 |
| Browser tests | `npm run test:e2e` runs three Playwright projects: `desktop` and `mobile` (the demo, and real accounts on the test database through the API on port 3102), and `email`, against a second API (port 3103) with `EMAIL_MODE=smtp` sending to Mailpit, whose API the tests read. `npm run test:performance` runs the 3,000-guest check on its own. `backend/test/e2e-tools.ts` changes the test database where the API rightly refuses (an event in the past, a Super User) | Adopted in Phase 17 |
| Image storage | `ImageStorage` (`backend/src/storage/`) keeps pictures on local disk under `UPLOAD_DIR` (a persistent volume in production), referenced by random keys and served at `/api/files/<key>`. Public, because the RSVP background is shown to guests without an account; keys are unguessable and never listed. Object storage can replace it behind the same interface | Adopted in Phase 13 |
| Data access boundary | UI reads and writes only through typed feature service interfaces. A mock provider and an API provider implement the same contracts; the provider is chosen once at the application boundary | `AGENTS.md` Frontend standards |
| Page tree | One shared set of pages and components for Demo Mode and the real app; no separate demo page tree | `AGENTS.md` Development strategy |

One AWS EC2 t4g.small (ARM) on the Free plan, running `deploy/docker-compose.yml`: Nginx (`deploy/web/`: the static React build, HTTPS by Let's Encrypt, `/api` proxied, `index.html` for page addresses), the API (`backend/Dockerfile`), PostgreSQL 17 and a `migrate` service that applies migrations before the API starts; volumes for the database, pictures and certificates. ## Public RSVP and RSVP Settings (Phase 9)

- **One component, two uses.** `features/public-rsvp/RsvpCard.tsx` draws the guest-facing page. The public page (`PublicRsvpPage.tsx`) passes it a form; RSVP Settings passes none, which makes it an inert preview. The preview therefore cannot drift from the real page.
- **No session.** The public page reads and writes through `Backend.publicRsvp` (`usePublicRsvp`), not through the session's services. A link of a demo event is answered from this browser; any other link by the API (`/api/public/rsvp/<slug>`).
- **Language.** The page is rendered inside `LocaleScope`, starting in the event's default RSVP language; the guest's switch changes only that scope.
- **Rules** for the settings live in `domain/rsvpSettings.ts` (message lengths, overlay, picture, calendar entry, YouTube address, the Google Calendar address). The page validates with the same function the provider uses.
- **Outside links.** Add to Calendar and Watch on YouTube are ordinary links that open in a new tab on the guest's click. Nothing is opened from the data layer.
- **Pictures** are reduced in the browser (`shared/imageTools.ts`) and sent as a data address. The demo keeps it with its data; the server stores it as a file and answers with its address (`/api/files/<key>`), which, sent back unchanged, keeps the picture.
- **QR code** is drawn as SVG from `qrcode-generator` (`features/rsvp-settings/qr.ts`) and downloaded as a PNG.
- **Other tabs.** A persistence adapter may report that another tab changed its stored value (`Persistence.onChange`, the browser's `storage` event). The mock services then re-read their data before the next operation, and `Backend.onExternalChange` lets `SessionProvider` reload what is on screen.
- **Development server.** The Excel libraries are loaded on demand, so they are listed in `optimizeDeps.include` in `vite.config.ts`; otherwise the server finds them late and reloads the page in the middle of an import or export.
