# Architecture decisions

Records the technical decisions approved in `AGENTS.md` and `PLAN.md`, plus the choices that are still open. Product behavior lives in `docs/PRD.md`; this file does not restate it.

Update this file when a decision is made or changed. Do not record a choice here as decided until it has actually been adopted in the repository.

## Decided

| Area | Decision | Source |
|---|---|---|
| Delivery order | Frontend-first and mock-driven: interactive React prototype → UX approval gate (Phase 12) → NestJS/PostgreSQL backend → API integration → Docker/AWS | `AGENTS.md` Development strategy; `PLAN.md` |
| Frontend | React + TypeScript, built with Vite. Scaffolded in `frontend/` (Vite 8, React 19, TypeScript 6, npm) | `AGENTS.md` Technical direction; `PLAN.md` Phase 1 |
| Frontend tooling | oxlint (lint), Prettier (format), Vitest + React Testing Library + jsdom (unit/component tests), Playwright (end-to-end), React Router (routing) | Adopted in Phase 1 |
| Styling | Plain CSS with design tokens as custom properties (`frontend/src/styles/tokens.css`) and CSS Modules per component. No CSS framework. Logical properties only, so one stylesheet serves LTR and RTL | Adopted in Phase 2 |
| Icons | `lucide-react` | Adopted in Phase 2 |
| Overlays | Dialogs, drawers and the mobile navigation use the native `<dialog>` element, which provides focus containment, Escape to close and focus return | Adopted in Phase 2 |
| Interface language | `i18next` initialised in `frontend/src/i18n/i18n.ts`; resources in `src/i18n/locales/{en,he}.json`; keys are type-checked. The chosen language is remembered in `localStorage` by `src/i18n/languageStorage.ts` — the one use of browser storage outside the demo persistence adapter, kept out of presentation components | Adopted in Phase 2 |
| Guest-facing language | `LocaleScope` (`src/i18n/LocaleScope.tsx`) renders a subtree in a fixed language and direction, independent of the interface language | Adopted in Phase 2 |
| Breakpoints | Below 768px: phone presentation (tables become cards). Below 1024px: sidebar becomes a drawer. 1024px and up: fixed sidebar | Adopted in Phase 2 |
| Responsive rendering | Where the phone and desktop presentations differ in structure (table versus cards), only the one that fits is rendered, chosen with `useMediaQuery` (`frontend/src/shared/useMediaQuery.ts`). Purely visual differences stay in CSS | Adopted in Phase 2 |
| Number, date and time formatting | `frontend/src/i18n/format.ts`, built on `Intl`. Dates and times take the event's time zone explicitly; `useFormatters` follows the language of the surrounding scope, including a guest-facing `LocaleScope` | Adopted in Phase 2 |
| Page title and focus | Each page sets the browser tab title through `useDocumentTitle`; after a navigation, focus moves to the main content (`frontend/src/app/RouteFocus.tsx`) | Adopted in Phase 2 |
| Data provider switch | `VITE_DATA_PROVIDER` = `mock` (default) or `api`, validated by `frontend/src/services/providerConfig.ts`. `createServices` builds the provider once at start-up and `ServicesContext` hands it to the application; `api` shows a not-available page until the backend exists | Adopted in Phase 1, wired in Phase 3 |
| Business rules | Pure TypeScript in `frontend/src/domain/`, with no React, storage or network. The mock provider calls them now; the backend enforces the same rules authoritatively later | Adopted in Phase 3 |
| Error codes | One `DomainError` type with stable codes (`FORBIDDEN`, `EVENT_READ_ONLY`, `DUPLICATE_PHONE`, `TABLE_FULL`, …) shared by every provider and translated for display by `describeError` | Adopted in Phase 3 |
| Service contracts | Promise-based interfaces in `frontend/src/services/contracts/`. A reusable contract test suite (`servicesContract.ts`) defines the behaviour any provider must have | Adopted in Phase 3 |
| Demo data | Generated by a seeded generator (`services/mock/generator.ts`) with a fixed seed and dataset version; dates are placed relative to the first launch. About 374 KB as stored | Adopted in Phase 3 |
| Demo storage | `localStorage`, one versioned entry (`event-planner.demo`), reached only through the persistence adapter in `services/mock/persistence.ts`. Data from another dataset version, or unreadable data, is discarded and regenerated | Adopted in Phase 3 |
| Stored-data versions | The demo dataset has `DATASET_VERSION` (4 since the phone-format change after Phase 6) and the accounts workspace its own `ACCOUNTS_VERSION` (`services/mock/state.ts`). Changing the generated demo content bumps only the first, so demo data is regenerated without touching what people created in preview accounts | Adopted in Phase 5 |
| Charts | Drawn with SVG and CSS inside the feature that needs them; no charting library. Every chart also states its figures as text or a table | Adopted in Phase 5 |
| Spreadsheet files | Excel files are read and written with `read-excel-file` and `write-excel-file` (MIT), loaded on demand so they are not in the main bundle. CSV is read and written by `frontend/src/domain/csv.ts`, with a UTF-8 byte-order mark so Excel opens Hebrew. Files are read in the browser and sent nowhere. The npm `xlsx` package was rejected as outdated with known vulnerabilities, `exceljs` as about ten times larger | Adopted in Phase 6 |
| Formula safety in exports | `neutralizeFormula` in `domain/csv.ts` writes a cell that would run as a formula as plain text; Excel cells are typed as text. Guest-typed values reach these files | Adopted in Phase 6 |
| Display preferences (guest columns, collapsed side menu) | `PreferencesService` in the service contracts; the mock provider keeps them per browser under `event-planner.preferences` through the persistence adapter, with no simulated delay | Adopted in Phase 6 |
| WhatsApp sending | `buildWhatsAppUrl` in `domain/messages.ts` builds the `wa.me` link; the provider returns it (`MessagePreview.launchUrl`) and never opens anything. The page opens it with `shared/openExternal.ts` directly from the user's click, before recording the send, so browsers do not block it as a pop-up. Tests replace `window.open` | Adopted in Phase 8 |
| Address state helper | `frontend/src/shared/useQueryParams.ts` applies each change on top of the last change requested, so quick successive changes are not lost | Adopted in Phase 6 |
| Session and workspaces | `SessionProvider` (`frontend/src/app/session/`) asks the provider who is using the application and gives the pages the data operations of that session; route guards send a signed-out visitor to the landing page. The provider (`Backend` in `services/contracts`) offers `auth` and `servicesFor(session)`. Until the backend exists, `services/mock/mockBackend.ts` holds two browser-local workspaces that never share data: the generated demo (`event-planner.demo`) and accounts created by the simulated sign-up (`event-planner.accounts`); the session is remembered in `event-planner.session`. All three go through the persistence adapter. In Phase 16 the accounts workspace is replaced by the API and the demo workspace stays | Adopted in Phase 4 |
| Simulated sign-in | Sign-up and sign-in on the mock provider are a simulation for reviewing the screens. No password is stored or verified. It is not authentication and must never guard real data | Adopted in Phase 4 |
| List state in the address | A list page keeps its filter, search and layout in the page address (query string), so a reload keeps them without using browser storage | Adopted in Phase 4 |
| Loading and error state | TanStack Query. Demo data changes only through mutations, which invalidate what they affect | Adopted in Phase 3 |
| Phone numbers | `frontend/src/domain/phone.ts`. `normalizePhone` turns any accepted form into one canonical form used for matching and uniqueness; a number without `+` is read as Israeli, and one local to another country is refused. `formatPhone` gives the form shown: local for Israeli numbers, with the country code for others. Guests and unknown responses store the shown form, so screens and exports agree | Adopted in Phase 3, extended after Phase 6 |
| Localization | `i18next` + `react-i18next`; locales `en` and `he`; root `lang`/`dir` follow the active locale; CSS logical properties | `AGENTS.md` Internationalization |
| Backend | Node.js + NestJS; thin controllers, rules in application/domain services | `AGENTS.md` Technical direction, Backend standards |
| Database | PostgreSQL, with Prisma for ORM and migrations | `AGENTS.md` Technical direction |
| Data access boundary | UI reads and writes only through typed feature service interfaces. A mock provider and an API provider implement the same contracts; the provider is chosen once at the application boundary | `AGENTS.md` Frontend standards |
| Page tree | One shared set of pages and components for Demo Mode and the real app; no separate demo page tree | `AGENTS.md` Development strategy |
| Demo Mode | Permanent public capability. Deterministic seeded fictional data, versioned, stored per browser profile, resettable, with simulated side effects. Never touches PostgreSQL and never authorizes anything server-side | `AGENTS.md` Demo Mode implementation; PRD §12 |
| Browser storage | Used only inside the demo persistence adapter, never from presentation components | `AGENTS.md` Frontend standards |
| Authorization | Enforced on the server for every event-scoped operation. Frontend permission checks are UX only | `AGENTS.md` Permissions, Security |
| Uploads | Stored through an abstraction that supports local storage now and object storage later | `AGENTS.md` Technical direction |
| Deployment target | One small EC2 instance (or comparable VM) running Docker Compose: Nginx serving the static React build and reverse-proxying NestJS, NestJS, PostgreSQL with a persistent volume. Images are built off-host where practical | `AGENTS.md` Technical direction; `PLAN.md` Phase 18 |
| Excluded infrastructure | No Kubernetes, microservices, Redis, message queues, managed RDS or background workers without a measured need and explicit approval | `AGENTS.md` Technical direction |
| Local development | The frontend runs without Docker, NestJS or PostgreSQL until the integration phases | `AGENTS.md` Technical direction |

## Repository structure

Current:

```text
/
  AGENTS.md          engineering rules (authoritative)
  CLAUDE.md          redirect to AGENTS.md
  PLAN.md            living implementation plan and progress log
  docs/              PRD and durable product/architecture documentation
  mockups/           UI reference images and their index (README.md)
  frontend/          React + TypeScript app (Vite)
```

Added when their phase begins:

```text
  backend/           NestJS + Prisma (Phase 13)
  scripts/           shared helper scripts, if needed
  docker-compose.yml single-VM stack (Phase 18)
```

Inside `frontend/`:

```text
  e2e/               Playwright end-to-end tests
  src/
    app/             router, route table, application-level layout and provider selection
    features/        one folder per page/feature (events, dashboard, guests, messages,
                     rsvp-settings, event-layout, event-settings, permissions, public-rsvp)
    domain/          domain types and business rules, independent of React and data source
    services/        provider choice, data hooks shared by the frame
      contracts/     service interfaces and the provider contract test suite
      mock/          demo provider: generator, state, persistence, services
    shared/          UI shared across features
      ui/            design-system components (buttons, fields, cards, tabs, dialogs, …)
      access/        read-only and role-restricted primitives
    app/shell/       application frame: sidebar, top bar, event selector, language switcher
    i18n/            language setup, translation resources, LocaleScope
    styles/          design tokens and base styles
    test/            test setup
```

Unit and component tests sit next to the code they cover as `*.test.ts(x)`.

## Routes

| Path | Page |
|---|---|
| `/` | Landing page; with a session, redirects to `/events` |
| `/signin`, `/signup` | Simulated sign-in and sign-up; with a session, redirect to `/events` |
| `/events` | Homepage / My Events (needs a session, as does every `/events/...` page and `/showcase`) |
| `/events/:eventId` | Redirects to the event's dashboard |
| `/events/:eventId/dashboard` | Dashboard |
| `/events/:eventId/guests` | Guests |
| `/events/:eventId/rsvp` | RSVP Settings |
| `/events/:eventId/messages` | WhatsApp Messages |
| `/events/:eventId/layout` | Event Layout |
| `/events/:eventId/settings` | Event Settings |
| `/events/:eventId/permissions` | Permissions |
| `/rsvp/:rsvpId` | Public RSVP (outside the event layout) |
| `/showcase` | Design-system showcase: the application frame and every shared component, with sample values |
| anything else | Not-found page |

These are client-side routes, so the production web server must serve `index.html` for unknown paths (tracked in `PLAN.md` Phase 18).
