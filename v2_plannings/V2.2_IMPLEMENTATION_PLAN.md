**Gaps and differences**

1. **"Up to 50 tables" is not in the documents.** The documents only have *maximum people*. Only the venue can add tables, so a table limit would only limit the venue itself. → Decision Q1.
2. **The documents go further than you asked.** Features you never mentioned:
   - three venue staff roles, with staff seeing only the events assigned to them;
   - a draft → publish → immutable *revisions* system for layout templates;
   - booking-overlap detection with setup/cleanup buffers and time-zone/DST handling;
   - a subscription state machine (TRIAL / PAST_DUE / SUSPENDED…);
   - a change-log;
   - a workflow for replacing the client lead.

   None of these is wrong, but together they add roughly 40% to the work. I recommend building a **core V2.2** first and the extras in **V2.3** (section 4).
3. **Template revisions are not needed** to keep your "events never change" rule. Each event already gets its own copy when it is created, so a template can be a normal editable saved layout. Dropping revisions saves about 3 days and makes the screens simpler.
4. **Navigation.** In your message, the venue has tabs: My Spaces and My Events. The PRD adds a workspace switcher (Personal | Venue). The two fit together: the switcher appears only for venue users, and the venue workspace has your tabs. Users with no venue see no change at all.
5. **Email must be turned on in production.** A client invitation is accepted through a verified email. In the current code, when email is off, sign-up marks the address verified automatically (D88), so client invitations need `EMAIL_MODE=smtp` (SES) in production.
6. **There are no mockups for the new screens.** `AGENTS.md` asks for a mockup for every page. → Decision Q10.
7. **The PDF was written against PRD v1.2 (17 Oct).** Later decisions are still compatible with it: D104–D110, which cover seats per table, adjustable limits, Brazil/Portuguese and versions. Nothing conflicts.

## 2. What already exists and helps

From reading the code:

- **A central permission check already exists.** `backend/src/access/event-access.service.ts` and `backend/src/domain/permissions.ts` check every event request. Today, though, almost every change uses one action, `EDIT`. The main groundwork is to split `EDIT` into smaller actions (Phase 1).
- **Seating is already separate from table editing.** Assigning a guest is `PUT guests/:id/table`. Table definitions are the `tables` controller, and the map geometry is `PUT layout` (positions only, with `layoutVersion` stale-save protection). Because these are already three endpoints, the client/venue split is cheaper than the spec assumes.
- **Email infrastructure is ready.** There is SMTP/SES/Mailpit, plus `EmailToken` with hashed, expiring, single-use tokens. It can be reused for client invitations.
- **Notifications (the bell) exist.** New kinds can be added to `NotificationKind`.
- **Event layout data lives on `Event`, `EventTable` and `VenueObject`.** A space template can store the same shape as JSON, checked by the existing `domain/layout.ts` rules. Creating an event then copies that JSON into new `EventTable` and `VenueObject` rows with new ids.
- **The frontend's mock and real providers share one contract** (`services/contracts`). Demo Mode will get a venue scenario through the same mechanism.

### 3a. Venue team roles (for Q6)

| What they can do | Venue Owner | Venue Manager | Venue Staff |
|---|---|---|---|
| Organization name, settings, (later) billing | ✅ | — | — |
| Add or remove team members | ✅ | — | — |
| Create, edit and archive spaces and layout templates | ✅ | ✅ | — |
| Create venue events and invite the client | ✅ | ✅ | — |
| Delete a venue event | ✅ | — | — |
| Change an event's date, address, max people, map and tables | ✅ | ✅ | optional |
| See which events exist | all | all | **only the events assigned to them** |
| See guest names, statuses, attendees and tables (no phones) | ✅ | ✅ | assigned events only |
| Export the seating list (no phones) | ✅ | ✅ | assigned events only |
| Edit guests, RSVP, messages or seating | — | — | — |

The last row is client-only for everyone on the venue side.

Example: the owner of the hall is the **Owner**. The events coordinator who meets couples and builds their events is a **Manager**. The shift manager who only needs the seating list on the night is **Staff**.

**Decision (2026-11-26): V2.2 builds Owner + Manager only. Staff is kept as an optional future feature.**

The reasoning for that choice: build Owner + Manager in V2.2. Staff needs "assign staff to events" screens and rules, which is about 3 more days, and is only useful once a venue has a bigger team. It can be added in V2.3 without changing anything else.

## 4. Scope

**Core V2.2 (this plan):**
- venue organizations (owner + managers);
- spaces;
- multiple named layout templates per space;
- venue My Events (All / Upcoming / Past);
- the create-event wizard, which copies the layout;
- client invitation with verified email and accept;
- client roles (Lead / Editor / Viewer);
- the two-sided event pages: client = guests, RSVP, WhatsApp and seating, with the map read-only; venue = map, tables and event details, with a read-only guest/seating view without phones;
- warnings and notifications for changes that affect seating;
- a same-day booking warning;
- the demo venue scenario;
- EN/HE/PT, mobile and RTL;
- a feature flag and a provisioning script.

**V2.3 (later), with rough sizes:**
- venue staff with assigned events (3d): **optional**, only if venues ask for it (owner, 2026-11-26);
- template revisions/publishing (3d);
- booking overlap with hours and buffers (2d);
- subscriptions, entitlements and payment provider (6–8d, after picking a provider);
- change-log viewer (2d);
- client-lead replacement workflow (1–2d);
- venue event duplication (1d);
- an end-of-relationship export/transfer process (2d).

## 5. Implementation plan

The estimates are **working days at the pace V1 was built** (Claude Code implements, you review and merge; V1 took about 6.5 weeks from 12 Oct to 26 Nov). Each phase is one PR. A phase is finished only when its tests pass, `PLAN.md` is updated and the existing test suite still passes, as `AGENTS.md` requires.

### Phase 0 — Decisions, documents, mockups · 1.5 days
- Record your answers to section 3 as decisions D111+ in `docs/DOMAIN.md`.
- Add the V2.2 section to `docs/PRD.md` and add phases 22–31 to `PLAN.md`.
- Move the V2.3 items into `docs/FUTURE_FEATURES.md`, including **Venue Staff (optional)**.
- Copy the open hosting and email options into `docs/FUTURE_FEATURES.md` "Deployment and operations", with a pointer to `HOSTING_PLAN.md`.
- Mockups and `resources/mockups/README.md` mapping for:
  - venue home (Spaces / Events tabs);
  - space details with its templates;
  - the template editor;
  - the create-venue-event wizard;
  - the invitation accept page;
  - the "maintained by the venue" locked state.
- **Test:** none (documents only). **Gate:** you approve the decisions and mockups.

### Phase 1 — Split permissions, no behavior change · 2 days
- Replace the single `EDIT` with smaller actions:
  - `EDIT_EVENT_DETAILS`, `EDIT_LAYOUT`, `EDIT_TABLES`;
  - `EDIT_GUESTS`, `ASSIGN_SEATING`, `EDIT_RSVP_SETTINGS`, `EDIT_MESSAGE`;
  - `EXPORT_GUESTS_FULL`.
- Update every controller in `backend/src/**` and the frontend's copy of `domain/permissions.ts`. Personal OWNER/ADMIN/VIEWER map to exactly what they can do today.
- **Test:**
  - a matrix test proving that every (role × action × past/upcoming) result equals today's result;
  - the full backend e2e and Playwright suites unchanged.
- **Gate:** zero changes in behavior. This is the safest place to find hidden permission coupling, before any venue code exists.

### Phase 2 — Database, additive migration · 2 days
- New tables: `Organization` and `OrganizationMember` (ORG_OWNER, VENUE_MANAGER), `VenueSpace` (name, address, maxPeople, maxTables?, timeZone, archived) and `SpaceLayout` (name, room size, floor picture, objects and tables as JSON).
- `Event` gets new columns:
  - `managementMode` (PERSONAL by default);
  - `organizationId?`, `venueSpaceId?`, `sourceLayoutId?`;
  - snapshot copies of the venue name and address.
- New client roles on event membership (CLIENT_LEAD / EDITOR / VIEWER) and an `EventClientInvitation` table (hashed token, expiry, status).
- New `NotificationKind` values.
- Capability rules for venue-managed events are added to the domain permission matrix and unit-tested.
- **Test:**
  - the migration runs on a copy of a database with existing events; every event becomes PERSONAL;
  - the migration also runs on a clean database;
  - matrix tests for the client and venue roles.

### Phase 3 — Venue workspace, frontend + mock (frontend-first) · 4.5 days
- Workspace switcher, shown only to venue members.
- Venue home with **My Spaces** and **My Events** tabs.
- Space create/edit/archive.
- **Template editor:** reuse `FloorPlan` and `ArrangementTab` by moving them off event data onto a "layout source" interface (the biggest frontend refactor in the project).
- Mock services plus a deterministic demo venue: 2 spaces, 3 templates, 4 events and a fictional client.
- **Test:**
  - component tests for the spaces and the template editor;
  - the existing event-layout tests still pass after the refactor;
  - the demo generator stays deterministic;
  - desktop/mobile × EN/HE/PT screenshots reviewed against the mockups.

### Phase 4 — Venue backend: organizations, spaces, templates · 3 days
- NestJS modules `organizations` and `spaces` with DTOs and validation (layout limits come from `domain/limits.ts`).
- Uploading the floor picture for a template, stored through the existing storage abstraction.
- The provisioning script `scripts/create-venue-organization`.
- `VENUES_ENABLED` flag on both backend and frontend.
- Connect the Phase 3 screens to the real API.
- **Test:**
  - backend e2e for CRUD;
  - **cross-organization isolation**: another org's member gets 404 on every route; guessed ids don't work;
  - with the flag off, the routes are closed.

### Phase 5 — Create a venue event (copy the layout) · 2.5 days
- Wizard: space → template → name/date/time → optional client email → review (people, tables, chairs, and a same-day booking warning).
- **One transaction** creates the event, copies the room, picture, objects and tables with new ids, and sets the snapshot fields. It copies no guests, RSVP answers or seating.
- Venue My Events: All / Upcoming / Past, filtered by space.
- "Awaiting client" state.
- **Test:**
  - the copied tables get new ids and keep the same numbers, shapes, capacities and positions;
  - editing or archiving the template afterwards leaves the event unchanged;
  - a failure in the middle rolls back everything;
  - a repeated request creates no duplicate event.

### Phase 6 — Client invitation and acceptance · 2.5 days
- The venue invites the client by email (EN/HE/PT template). The invitation link uses a hashed, single-use, expiring token.
- Accept page:
  - a signed-in user whose email matches accepts the invitation;
  - a new user signs up, verifies the email, then accepts.
- The venue can resend or revoke the invitation.
- The client's My Events shows the event with a "Managed by <venue>" badge.
- **Test:**
  - a wrong email cannot accept;
  - an expired, revoked or already-used link fails;
  - the response never reveals whether an email has an account;
  - legacy personal-event sharing still works as before.

### Phase 7 — The shared event, two sides · 4.5 days
Every event page decides what to show from the capabilities:
- **Client side:**
  - Event Settings shows the venue details (date, address, max people) read-only, with a "maintained by the venue" note, and RSVP settings editable;
  - Guests, RSVP, Messages and Dashboard work as today;
  - Event Layout shows the map read-only and Manage Guests (seating) enabled;
  - on mobile, the table list is used for seating;
  - Permissions: the Lead invites Editors and Viewers.
- **Venue side:**
  - Dashboard;
  - a read-only guest/seating view (name, status, attendees, table; no phones);
  - a seating export without phones;
  - map, tables and event details editable;
  - no access to guest editing, RSVP settings or messages.
- **Test (security):** direct API calls from each role to each endpoint (the spec's V22-07…V22-11 list):
  - the client cannot PATCH the address, capacity, tables or layout;
  - the venue cannot change guests, RSVP or messages, and cannot export phones;
  - Playwright runs one full venue → client flow.

### Phase 8 — Changes that affect the client · 2 days
- The venue deletes an occupied table or lowers its chairs:
  1. a dialog shows the affected guest parties and attendees;
  2. the venue confirms;
  3. one transaction unassigns those guests;
  4. the client gets a notification.
- Changing the date, address or max people also notifies the client. Seating conflicts appear as a warning on the venue Dashboard.
- **Test:**
  - nothing is lost silently;
  - a stale save is rejected (`layoutVersion`);
  - a notification is created exactly once.

### Phase 9 — Demo, translations, accessibility, full regression · 3 days
- Demo: switch between "Venue owner" and "Client" in the demo venue scenario, with no real side effects.
- Hebrew and Portuguese texts for everything new.
- RTL, 320px mobile and keyboard checks.
- Playwright scenarios V22-01…V22-20, apart from the items moved to V2.3.
- **Test:** the complete old and new suites; 80% coverage on the new domain and service code.

### Phase 10 — Release · 2 days
- **Blocked until hosting and email are chosen** (`HOSTING_PLAN.md` §8). Setting up hosting is about 2 more days (§7 there) if no server exists by then. Until then, Phases 0–9 run and are tested locally, with emails caught by Mailpit (`backend/docker-compose.dev.yml`), and the demo is published on Netlify.
- Back up the production database, then migrate.
- Deploy with `VENUES_ENABLED=false` and smoke-test personal events.
- Turn the flag on for one test organization, then the pilot venue.
- Update `README.md` (settings), `docs/DEPLOYMENT.md` (email must be on, provisioning script, how to turn the flag off) and `docs/ARCHITECTURE.md`.
- **Rollback:** turn the flag off. The new tables stay; there is no down-migration.

## 6. How testing is organized

- **Every phase:** lint, typecheck, unit tests, backend e2e (`backend/test/*.e2e-spec.ts`), frontend component tests, and the existing Playwright suite. The old suite must stay green.
- **Security:** one table-driven test that calls every event endpoint as each role (personal Owner/Admin/Viewer; client Lead/Editor/Viewer; venue Owner/Manager; another org's member; a stranger) and checks the result against the capability matrix. It is added in Phase 1 and grows with each phase.
- **Migration:** run against a database copy that holds today's data shapes, as well as a clean database.
- **Manual:** each new screen in desktop/mobile × EN/HE/PT, compared with the mockups.
